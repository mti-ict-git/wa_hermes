# Security and Access Model

## Purpose
Define the trusted security boundary for the WhatsApp helpdesk channel so model output never becomes the source of truth for identity, authorization, or backend execution.

This document is the source of truth for:
- trusted caller identity derived from OpenWA metadata
- technician versus regular-user role resolution
- HMAC-signed `AuthContext`
- validator responsibilities before any backend adapter call
- redaction and audit requirements for downstream results

## Trust Boundary

### Trusted Inputs
The system may trust only:
- OpenWA transport metadata received by the webhook
- locally normalized sender phone
- local technician contact matching
- local AD-backed eligibility lookup
- server-generated correlation ids, timestamps, and signatures

The system must not trust:
- free-text role claims from WhatsApp users
- target usernames or phone numbers claimed in natural language
- model-generated role upgrades
- model-generated authorization decisions

## Role Resolution

### Input Source
Role resolution uses WhatsApp metadata only:
1. read sender id and sender phone from OpenWA metadata
2. normalize the phone number locally
3. exact-match the normalized phone number against the technician contacts source
4. default to `user` when no technician match is found

### Role Rules
- `technician`
  - exact normalized phone match in technician contacts
- `user`
  - any eligible sender who is not an exact technician match
- `unregistered`
  - sender fails local eligibility policy

No model output may change the resolved role.

## AuthContext

### Purpose
`AuthContext` is the signed trusted envelope generated by the server and attached to the typed-intent workflow. It proves who the caller is, which role was resolved, and which policy snapshot was applied.

### Required Fields
```json
{
  "auth_version": "v1",
  "source": "openwa",
  "chat_id": "6285712612218@c.us",
  "chat_type": "private",
  "sender_id": "6285712612218@c.us",
  "sender_phone": "6285712612218",
  "role": "technician",
  "is_registered_user": true,
  "session_key": "wa:private:6285712612218@c.us",
  "session_id": "run_xxx",
  "policy_version": "2026-08-20",
  "request_id": "req_xxx",
  "issued_at": "2026-08-20T06:30:00.000Z",
  "expires_at": "2026-08-20T06:32:00.000Z",
  "nonce": "random-unique-value",
  "signature": "base64url(hmac_sha256(secret, canonical_payload))"
}
```

### Signing Rules
- signing happens only inside the WhatsApp bridge
- signature uses HMAC-SHA256 with a server-held secret
- the secret must never be exposed to Marisa, OpenWA, or adapter outputs
- verification must fail closed on:
  - missing signature
  - mismatched signature
  - expired context
  - nonce replay
  - unsupported `auth_version`

### Lifetime Rules
- `AuthContext` should be short-lived
- recommended TTL: 60-120 seconds
- each request gets a fresh `request_id` and `nonce`
- replayed or stale contexts must be rejected before adapter execution

## Authorization Model

### Default Rule
- default deny
- allow only explicitly mapped role + intent combinations

### Authorization Check Order
1. verify `AuthContext` signature and TTL
2. verify role and chat type
3. verify typed intent schema
4. verify target scope rules
5. verify adapter allowlist
6. execute allowed adapter call

### Target Scope Rules
- `user`
  - may operate only on self-scoped read-only intents
  - may not choose arbitrary targets
- `technician`
  - may use approved technician intents
  - may target other users only through validated references
  - may not pass raw LDAP filters, DNs, shell fragments, or arbitrary field requests

## Data Minimization

### Allowed Data to Reach Marisa
- trusted sender identity summary
- signed role and chat context
- typed intent result summaries
- redacted backend result fields

### Forbidden Data to Reach Marisa
- LDAP bind credentials
- raw directory objects
- unrestricted group membership dumps
- recovery secrets
- passwords
- raw Veeam backend payloads when a redacted summary exists

## Redaction Rules
- redact full phone numbers when not needed
- redact secrets, tokens, bind credentials, and internal stack traces
- redact fields not explicitly allowlisted per adapter contract
- present stable operator-facing error codes instead of backend internals

## Audit Requirements
Every execution attempt must record:
- `request_id`
- `operation_id`
- resolved role
- sender phone hash or masked value
- target reference
- typed intent name
- allow or deny decision
- policy version
- adapter invoked
- result code
- latency

Every denial must also record:
- denial reason
- validator stage that rejected the request
- whether the failure came from signature, role, schema, scope, or adapter policy

## Acknowledgement Policy
- WhatsApp should receive a quick ACK before model intent generation for long-running flows
- recommended default ACK:
  - `Baik, permintaan sedang diproses.`
- ACK does not imply authorization success
- final allow or deny still depends on signed context and validator checks

## Non-Goals
- no direct Marisa access to raw AD or Veeam backends
- no trust in prompt-only policy language
- no authorization decisions delegated to the model
